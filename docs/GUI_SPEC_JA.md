# GUI付き完成版の実装仕様案（設計のみ・実装未着手）

## 目的・段階

第一目標はrootlessの**クローズドβ版が安全に導入・停止・復旧できること**。GUIはその後の第二段階で実装する。SileoなどのパッケージマネージャーによるインストールUIと、アプリの設定UIは別物。

推奨初期方式：TheosによるPreference Bundle（iOS設定アプリ内）＋既存Pythonバックエンド。独立アプリは、複数ページのオンボーディングや通知・状態可視化の必要性が明確になった場合に比較再検討。**ネイティブビルド、署名、ABI、サンドボックス、設定画面からの安全なIPCは実機未検証**。

## 画面と機能

| 画面 | 表示する情報 | 操作 |
|---|---|---|
| 起動・診断 | rootless互換、Python/sqlite3/ssl、DBスキーマ、権限の合否 | 診断を実行 |
| 初期設定 | HTTPS送信先、source_id、ユーザー指定のDB、マスクされた秘密トークン | 設定保存（既定はOFF） |
| ダッシュボード | 同期ON/OFF、キュー件数、固定再送待ち、最終受信OK時刻 | 有効化／停止／手動実行 |
| 問題の確認 | エラーコード、再試行待ち、長文保留、空き容量の警告 | 安全な対応説明を表示 |
| データとプライバシー | 保存先、暗号化バックアップ方針、外部送信の同意 | 削除・出力は確認画面（将来） |
| ヘルプ | 対象範囲・OpenChat非対応・復旧/連絡先 | ローカルのガイドを表示 |

初期セットアップでは**勝手にLINEのDB探索・送信・有効化を行わない**。端末内の実LINEデータをGUIに表示せず、エラー診断は件数とコードだけを示す。

## バックエンド契約案（まだ実装しない）

既存CLIの許可済み操作 `init`, `configure`, `doctor`, `status`, `enable`, `disable`, `run` だけを呼ぶ。将来の内部IPCもコマンドを固定し、任意のシェル文やroot権限をGUIから実行できないようにする。

- 設定画面はローカルの設定とステータスを読み取る最小権限で起動。
- 秘密トークンは引数、URL、診断ログ、クリップボード、画面キャプチャ、クラッシュレポートに出さない。受け渡しは適切に保護されたローカル経路を使い、保存方法・権限を実機で検証する。
- `run` は確認後の手動送信のみ。二重実行を防ぎ、処理中は重複操作を無効化。
- `doctor` のテキスト出力を直接パースするのではなく、将来JSONスキーマを定義して安全な診断コードを返す。
- `status` にメッセージ本文や個人IDを含めない。メッセージキューの詳細プレビューは初期バージョンでは提供しない。
- GUIの更新・アンインストールと、秘匿状態データの保持・完全削除は別操作にする。

## 状態遷移案

`未初期化 → 設定済み・無効 → 診断成功・無効 → 有効・待機 → 手動送信中 → 完了/再試行待ち`

どの状態からでも「安全に停止」を選べる。ただし実行中の送信を途中で殺して受信側が不明状態にならないように、キューを保持して再開できることが条件。

不正なDB、送信先の変更、破損した固定バッチ、実機非対応、受信側の仕様不一致は**エラー停止**。ユーザーに単純な「リセットして直す」を勧めない。

## デザイン指針

- 大きいON/OFFと接続状態を一目で確認。未送信件数・再試行待ち・最終送信結果を区別する。
- 初回起動時はオフ、端末や同意が未検証なら有効化ボタンを出さない。
- 日本語UIを先行し、エラー表現は「通信先に受理されたか不明」「長文が保留」など、行動に結び付く説明にする。
- VoiceOver、Dynamic Type、ダークモードを想定した階層で設計。
- テスト用スクリーンショットには架空値のみ使用。
