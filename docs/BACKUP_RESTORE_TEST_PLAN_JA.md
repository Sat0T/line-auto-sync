# RC3のバックアップ・復旧計画（実機未実施）

この資料は**配布候補の新規環境のみ**を想定した設計・検証手順であり、稼働中の個人用iPadや本番のLINE転送・GAS・通知・カレンダー・タスク台帳を変更する指示ではない。実機での実施には別途明示的な許可が必要。

## バックアップ対象（すべて非公開）

- 端末内のLineAutoSync `config/config.json`：送信先とトークンを含む
- `state/normal-delivery.sqlite`：収集位置、未送信本文、固定済みバッチ、送信ACK、送信時刻を含む
- `state/named-cache.sqlite`：会話相手やチャットの表示名を含む
- `state/dbpath` と、旧版から移行する場合のみ `sentid`, `initial_scan_id`, `new.csv`, `sent_at` 等の移行元状態
- `-wal`, `-shm` が存在する場合、それぞれの一貫性を壊さないこと

**LINE本体のDBはこのパッケージのバックアップ対象としてコピーしない。** 参照先の存在・権限は別途確認する。

## 一貫した取得手順の設計

1. 手動送信プロセスを停止し、処理中でないことを確認する。ほかのレガシーワーカーとの同時実行は禁止。
2. 設定・状態ファイルの所有者、アクセス権、バージョンと同期元IDを確認する。画面・ログに秘密値を出さない。
3. SQLiteの**オンラインバックアップAPI**を使い、元DBとWALの一貫したスナップショットを新しい非公開ファイルへ取得する。アクティブなSQLite本体だけをファイルコピーしない。
4. 対応するconfig、ポインター、キャッシュ、移行状態を同一時点の1セットとして保存する。
5. 外部保存する場合は暗号化・アクセス制御・保存期間・削除方法を確認する。公開リポジトリ、Issue、チャットの添付に実バックアップを送らない。
6. 復元前に元セットを保護し、**別の隔離環境**で整合性・source_id・送信先と固定リクエストを確認する。勝手に新しい受信先へ転送しない。
7. `normal-delivery.sqlite`のapplication_id、messages/delivery/meta、未送信件数、固定body/ids/試行回数、ACK位置を比較する。
8. 配布版のコードと状態スキーマが一致することを確認する。古いRC2へ新しいキューをそのままダウングレードしない。

## 模擬テストの根拠

`tests/test_delivery.py` では合成DBに収集行・未送信キューと固定再送リクエストを作り、SQLite `Connection.backup` によるスナップショットを独立した状態ディレクトリで読み直すテストを追加した。

検証対象：収集位置、pending、frozen、固定body、対象PK、リトライ回数。

**実機のWAL競合、復旧後の実GAS通信、権限・暗号化・バックアップストレージの安全性は未検証。** バックアップ成功と受信側の重複排除は別問題。

## 異常時の方針

### 既存状態DBの検査（2026-10-29追加、合成環境のみ）

既存DBを開く際は、読み取り専用スナップショットでapplication_idと既知のテーブル定義を照合する。不足テーブル、異なる制約、不明なテーブル/view/trigger、読めないSQLiteは拒否し、CREATE TABLEで自動修復しない。新規DBだけが初期化対象で、テーブル3つとapplication_idを同じトランザクションで作る。

`unsupported_or_corrupt_delivery_schema` / `unreadable_delivery_database` / `foreign_or_incomplete_delivery_database` の場合、状態DBを削除して再初期化しない。元ファイルとWAL等を保全し、対応するコード・設定・一貫したバックアップを別の隔離ディレクトリで検査する。未知の将来スキーマも拒否するため、更新時は明示的な移行手順が必要。

合成テストでテーブル欠落後にHTTP・ACK・テーブル再生成が起きないこと、欠落前のSQLite APIバックアップで収集位置・pending・固定body/idsを復元できること、制約欠落・trigger・壊れたヘッダ・初期化途中停止を拒否することを確認した。これは全ページ/全内容の破損診断や実機復旧の証拠ではない。大きなキューを毎回走査する完全整合検査は追加していない。

さらに既存DBの必須meta（identity/initial_baseline/acked/collected）欠落、不正な形式・範囲、非有限/負の成功時刻を拒否する。metaが空でもmessages/deliveryが残っている場合は新規扱いしない。初回収集前の空DBは許可する。旧CSV移行時はACKが収集位置を超える場合があるので、その大小だけで破損判定しない。すべての行とmetaが既に消去されている状態を、外部の証跡なしに新規の空DBと区別できるわけではない。

- DB破損：破損前のセットで隔離復元。cursorやACK値を「適当に進めて」解消しない。
- 送信結果不明：受信側dedupeがない限り二重処理の危険。凍結バッチを削除しない。
- データ量の増加：未送信データを消すのではなく、容量・保存期間・長文上限の方針を決める。
- 端末アンインストール：パッケージのコードとprivate stateは別。自動的な会話データ消去も行わない。
- 移行失敗：旧CSVや旧カーソルをそのまま保存し、RC3の移行を中断する。旧版と新版を同時起動しない。

## β版承認前に追加で必要な証拠

- 独立rootless端末でのインストール／無効化／アンインストール／復元
- SQLite WAL利用中の整合バックアップと保存先の権限
- 暗号化バックアップの運用、保存・削除と第三者データの同意
- ガイドに従って別端末で復旧した後の合成データ送信
- 不完全な復旧を安全に拒否できること
