## 統合前に見つけた具体的な問題

### 1. 保存済みバッチの意味的破損をACKする可能性（重要）

**以前の挙動:** 凍結していた `delivery.body` と `delivery.ids` は、次回の送信時に相互一致やキューとの対応を再検査しない。保存されたJSONのIDが正常にパースでき、HTTPが `OK` と返った場合、**実際の送信本文に含まれない別のPKをACK済みにする恐れ**があった。古いコードは不正なJSONだけは再試行失敗として扱っていたが、整形式で内容が不正なケースが未検証だった。

**対策:** `DeliveryState.verify_frozen` を追加し、実送信の直前にmanifest、source、B/C1復元、全レコードPK、キュー内PKと未ACK状態、原文のハッシュ、本文のテキスト、batch_id、canonical SHA256が一致することを確認。矛盾があれば `corrupt_frozen_delivery` で**送信せず停止**し、ACK/キューを進めない。これは悪意ある同一権限のプロセスに対する暗号学的保護ではなく、既存キューの整合性を自己診断する安全策。

### 2. 受信側モデルが正常な時刻順バッチを拒否（重要）

`legacy_names.finalize_body` は時刻とPKでソートするが、模擬受信者は全PKが昇順でなければ拒否していた。タイムスタンプがPKの大小と逆転すると、送信側が作った**正当なバッチを模擬受信側が拒否**する。この誤った前提を除去して、PKの一意性・`maxid=max(PK)`・manifest hashは保持。送信側から模擬受信モデルまでの逆転したタイムスタンプで回帰テストを追加。

**注意:** これは模擬受信モデルの修正であり、実GASの仕様が一致したことを意味しない。実受信者が「PK昇順」を要求するなら実受信側の修正または明示的なプロトコル変更が必要。

### 3. トークン更新の反映タイミング（中）

従来は凍結前に読み込んだ認証トークンを送信時に再利用していた。凍結後の有効なトークン更新が送信前に行われた場合、旧トークンで送信してしまう。送信時の再検証済み設定からトークンを取得するよう変更。HTTP処理中の設定変更を完全にロックするものではない。

### 4. Unixミリ秒タイムスタンプ診断と収集の不一致（重要）

`cli.doctor` が受理していたSQLite REALの小数タイムスタンプを、`Resolver` は数字文字列とみなせず拒否する。さらに `normalize_row` は小数を一旦キューに取り込み、収集カーソルを進め得た。**Doctorと収集をResolverの想定する整数Unixミリ秒に統一し、不正なら収集位置を進めずトランザクションをロールバック**する。
